## Overview

存档与读档系统是《足球小镇》的持久化基础，负责把小镇状态、球员数据、资源余额、赛季进度、解锁内容和关键节点状态保存为一致、可验证、可恢复的快照。它不定义训练、比赛、建设或经济的具体内容，而是保证这些系统在退出、重进、版本更新或异常中断后，仍能回到正确的时间点继续推进；同时为未来的版本迁移、数据校验与恢复策略预留空间，让玩家始终相信长期投入不会丢失，随时回来都能无缝接上上一次的进度。

## Player Fantasy

存档与读档系统服务的玩家幻想是：“我的足球小镇会一直稳稳地延续下去。”玩家未必会主动注意这个系统，但他们必须持续感到安心：无论是刚完成一轮训练、打完一场关键比赛，还是推进到赛季结算前后，自己的投入都被可靠地保留下来，不会因为退出游戏、切换设备环境、异常中断或版本更新而轻易失去。

这种幻想的重点不是“频繁手动管理存档”，而是“长期经营可以被信任”。玩家应该相信，自己今天做出的培养、建设和资源分配决策，明天回来仍然会完整存在；即使系统发生中断，也能回到一个清晰、合理、可继续推进的状态。对《足球小镇》这种强调低压力长期成长的游戏来说，存档与读档系统必须把“可随时离开、可安心回来、长期投入不会白费”的稳定感变成体验底座。

## Detailed Rules

### Core Rules

1. 存档与读档系统是长期进度的唯一权威持久化入口。任何会影响长期状态的系统，都必须通过本系统登记并写入一致性快照；下游系统不得各自维护彼此冲突的独立权威存档。
2. 一个“游戏存档”必须至少包含以下五类内容：
   - 存档元数据：存档 ID、存档名/显示名、创建时间、最后保存时间、累计游玩时长、数据版本、兼容状态、最近稳定节点；
   - 小镇状态：设施、等级、布局、已解锁建设内容、进行中的建设进度；
   - 球员与队伍状态：球员列表、属性、潜力、状态、技能/特性、阵容配置、队伍相关长期状态；
   - 资源与成长状态：经费、研究点数、运动点数、阶段奖励、长期解锁、声望/成就相关已确认结果；
   - 时间与赛季状态：当前时间轴位置、当前阶段、当前赛季、赛程节点、待处理结算节点、下一关键节点上下文。
3. 本系统保存的是“可继续推进的整体世界状态”，而不是单个子系统的局部片段。任何一次有效保存，都必须保证资源、球员、小镇与赛季进度来自同一时间点。
4. 本系统必须区分稳定节点与瞬时节点。常规保存只能在可验证的稳定节点生成；稳定节点至少包括 `Planning`、`Match Trigger`、`Post-Match Settlement`、`Stage Settlement`、`Season Settlement`、`Offseason`，以及 `SeasonStart` 完成后的返回节点。
5. `Match In Progress`、未完成的行动结算、尚未提交的奖励选择、以及其他“时间已推进但结果未落地”的中间态，不能被当作标准可恢复存档点直接写入。
6. 如果玩家或系统在瞬时节点发起保存请求，本系统必须明确采用以下两种方式之一：延后到最近下一个稳定节点执行，或阻止本次保存并清晰说明原因；不得静默写出半完成状态。
7. 本系统必须同时支持手动保存与自动保存，但两者共享同一套一致性与校验规则；自动保存不能因为“后台触发”而降低数据完整性要求。
8. 自动保存必须优先覆盖“高价值且跨系统影响大”的节点，至少包括：完成一次日常行动结算后、完成赛后结算后、完成阶段结算后、完成赛季结算后，以及确认重大解锁或阵容/建设长期变更之后。
9. 任何一次保存，在玩家体验层都必须表现为原子结果：要么新快照完整可用，要么保留之前最后一个有效快照；不得出现“新旧各保存一半”的可见结果。
10. 读档必须先做完整性校验，再做版本兼容性判断，再进入状态恢复；校验失败的档案不得直接套用到当前世界状态。
11. 如果旧版本存档仍在支持范围内，本系统必须先完成版本迁移，再允许读档成功；迁移后的结果必须重新通过一致性校验，才能成为新的有效快照。
12. 如果存档损坏、缺失关键字段、或版本超出支持范围，本系统必须进入恢复流程：优先回退到最近一个有效自动存档或备份快照；若无可恢复项，必须明确告诉玩家该档案不可继续使用。
13. 本系统必须保存“最近稳定节点语义”，使读档后能回到一个玩家可理解、可继续操作的入口，而不是回到结算一半、奖励半领、比赛半开始的模糊状态。
14. 读档完成后，下游系统只能根据恢复后的权威状态重建运行时缓存、UI 展示和临时派生值；任何派生缓存都不得在读档时反向覆盖权威存档数据。
15. 本系统必须为 UI 提供可展示的存档摘要字段，至少包括：存档名、最后保存时间、累计游玩时长、当前赛季/阶段、关键资源概览，以及最近稳定节点类型。
16. 覆盖存档、删除存档、或载入另一进度前，系统必须明确提示将要影响的目标存档；任何会放弃当前未保存长期进度的操作都不得静默发生。
17. 本系统的 MVP 目标是“可靠恢复长期经营进度”，不是“支持任意时刻自由回滚到瞬间态”。如果两者冲突，必须优先保证一致性、可验证性和可恢复性。
18. 任何下游系统若希望新增必须持久化的长期字段、改变快照边界、或允许新的中间态可恢复，必须先回到本系统修订接口，而不能在本地文档中默认“顺带保存”。

### States and Transitions

| State | Description | Enter condition | Exit condition | Valid next states |
|---|---|---|---|---|
| Ready | 当前没有进行保存或读档流程，系统处于可接收请求状态 | 游戏启动完成、一次保存/读档结束、恢复流程结束 | 玩家或系统发起保存/读档请求 | Save Requested / Load Requested |
| Save Requested | 已收到一次保存请求，正在判断是否允许立即保存 | 玩家手动保存、自动保存触发器命中 | 已判定当前是否为稳定节点 | Snapshot Assembly / Save Deferred |
| Save Deferred | 保存请求已登记，但当前处于不可直接落档的瞬时节点 | 在 `Match In Progress` 或其他未完成结算阶段触发保存 | 到达最近稳定节点，或请求被取消/失效 | Snapshot Assembly / Ready |
| Snapshot Assembly | 正在从各系统收集本次快照所需的权威状态 | 保存请求获准执行 | 所有必需字段已收集完毕 | Snapshot Validation |
| Snapshot Validation | 正在检查快照完整性、一致性和必要字段 | 快照组装完成 | 校验通过或失败 | Save Commit / Recovery |
| Save Commit | 正在把已校验快照提交为新的有效存档 | 快照校验通过 | 提交成功或失败 | Ready / Recovery |
| Load Requested | 已收到读档请求，正在锁定目标存档并准备检查 | 玩家选择某个存档，或系统要求恢复最近有效档 | 目标存档已被定位并读取元数据 | Load Validation |
| Load Validation | 正在检查目标存档的完整性、版本和兼容性 | 目标存档已打开 | 校验通过、需要迁移或不可用 | Migration / State Restore / Recovery |
| Migration | 正在把旧版本可兼容存档转换到当前支持结构 | 目标存档版本可迁移但不可直接恢复 | 迁移成功并复检通过，或迁移失败 | State Restore / Recovery |
| State Restore | 正在把存档中的权威状态恢复到当前运行世界 | 目标存档已通过校验/迁移 | 所有权威状态恢复完毕，并完成下游重建 | Ready |
| Recovery | 保存、读档、校验或迁移失败后的恢复分支 | 任一关键步骤失败或发现损坏档 | 已回退到最近有效快照、返回安全入口或告知玩家失败结果 | Ready / Load Requested |

### Interactions with Other Systems

| System | 存档与读档系统提供 | 该系统提供回存档与读档系统 | Ownership boundary |
|---|---|---|---|
| 数值系统 | 共享数值类别的持久化入口、版本化快照边界、一致性恢复点 | 权威属性值、资源值、共享数值状态字段定义 | 存档系统定义“哪些数值必须被保存以及何时写入”；数值系统定义“这些数值本身代表什么” |
| 时间与赛季推进系统 | 稳定节点恢复、时间状态快照、赛季进度回放入口 | 当前时间轴位置、当前阶段、赛季进度、待触发关键节点、稳定节点语义 | 存档系统定义“如何保存/恢复推进状态”；时间系统定义“哪些节点可被安全恢复” |
| 运动员培养系统 | 球员长期成长数据的持久化容器 | 球员 roster、属性/潜力、训练结果、技能/特性、状态变更 | 存档系统定义“训练结果何时落档”；培养系统定义“球员数据结构与成长含义” |
| 比赛竞技系统 | 比赛前后可恢复节点、赛果落档时机、异常退出恢复策略 | 已确认的比赛结果、赛后奖励、比赛相关长期状态变化 | 存档系统定义“不保存半场中的未定态”；比赛系统定义“哪些结果已被视为最终确认” |
| 经济管理系统 | 周期账期与资源状态的统一持久化 | 收入/支出结算结果、账期状态、长期费用或收益字段 | 存档系统定义“账目何时与其他系统一起快照”；经济系统定义“具体收支内容” |
| 小镇建设系统 | 建设队列、完工进度与布局状态的恢复入口 | 建筑列表、等级、布局、工期进度、已完成效果 | 存档系统定义“建设状态如何被整体恢复”；建设系统定义“建设内容本身与效果” |
| 联赛与赛事结构系统 | 赛程与排名的持久化框架 | 当前联赛层级、赛程表、积分/排名、晋级/降级相关长期状态 | 存档系统定义“赛事容器如何随赛季一起保存”；赛事系统定义“赛事结构与规则细节” |
| 声望与成就系统 | 已确认长期解锁与已领取奖励的持久化 | 声望等级、已解锁内容、已完成成就、已领取奖励标记 | 存档系统定义“哪些结果必须被永久保留”；声望系统定义“哪些条件算达成” |
| 主循环 UI 框架 | 存档列表摘要、保存/读档结果、冲突与错误提示语义 | 存档入口、确认流程、展示优先级、失败反馈界面 | 存档系统定义“哪些存档信息可展示”；UI 系统定义“如何让玩家操作和理解这些信息” |
| 球员管理 UI | 已恢复球员状态的权威来源 | 当前查看目标、排序偏好等可选展示上下文 | 存档系统只负责长期权威数据；球员 UI 负责展示层偏好是否需要单独保留由后续 UI 规则决定 |
| 建设与经营 UI | 已恢复建设/经营状态的权威来源 | 当前选中建筑、过滤条件等临时展示上下文 | 存档系统优先保证长期经营状态恢复；展示层临时态是否持久化不由本系统默认拥有 |
| 教程与提示系统 | 保存失败、恢复成功、兼容迁移等可提示事件语义 | 面向玩家的说明文本、引导节奏和风险提示展示 | 存档系统定义“发生了什么”；提示系统定义“怎样告诉玩家” |
| 存档与读档系统 | 全局一致性快照、兼容迁移、恢复路径 | - | 本系统拥有快照边界、版本校验和恢复策略；不拥有下游系统的业务内容定义 |

## Formulas

### 1. 存档快照完整度判定

`save_snapshot_completeness` 的公式定义如下：

`save_snapshot_completeness = present_required_fields / total_required_fields`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| 已存在必需字段数 | `present_required_fields` | int | 0–`total_required_fields` | 当前快照中已成功写入且可读取的必需字段数量 |
| 必需字段总数 | `total_required_fields` | int | > 0 | 当前版本规范要求必须存在的字段总量 |
| 快照完整度 | `save_snapshot_completeness` | float | 0–1 | 用于判断一个快照是否具备成为有效存档的基础完整度 |

**Output Range:** 0–1；只有当结果为 `1` 时，快照才可进入“完整快照”判定流程。  
**Example:** 若当前版本要求 `40` 个必需字段，而快照中成功写入 `40` 个，则 `save_snapshot_completeness = 40 / 40 = 1`。

### 2. 跨系统一致性校验通过率

`cross_system_consistency_ratio` 的公式定义如下：

`cross_system_consistency_ratio = passed_consistency_checks / total_consistency_checks`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| 通过的一致性校验数 | `passed_consistency_checks` | int | 0–`total_consistency_checks` | 快照在资源、球员、小镇、赛季等跨系统关系上通过的校验项数 |
| 一致性校验总数 | `total_consistency_checks` | int | > 0 | 本次保存或读档恢复前要求执行的总校验项数 |
| 一致性通过率 | `cross_system_consistency_ratio` | float | 0–1 | 衡量该快照是否满足跨系统一致性的共享判定值 |

**Output Range:** 0–1；只有结果为 `1` 时，快照才可视为一致。  
**Example:** 若一次保存需执行 `12` 项一致性检查，而全部 `12` 项通过，则 `cross_system_consistency_ratio = 12 / 12 = 1`。

### 3. 可恢复稳定节点判定

`recoverable_stable_node` 的公式定义如下：

`recoverable_stable_node = current_runtime_node ∈ stable_node_set`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| 当前运行节点 | `current_runtime_node` | enum | runtime node set | 当前游戏流程所在节点，例如 `Planning`、`Match Trigger`、`Match In Progress` 等 |
| 稳定节点集合 | `stable_node_set` | set | predefined set | 本系统允许作为标准恢复点的稳定节点集合 |
| 是否为可恢复稳定节点 | `recoverable_stable_node` | bool | true / false | 当前节点是否允许直接生成标准可恢复存档 |

**Output Range:** 布尔值；为 `true` 时允许进入标准保存流程，为 `false` 时必须延后保存或阻止保存。  
**Example:** 若 `current_runtime_node = Post-Match Settlement`，且该节点属于 `stable_node_set`，则 `recoverable_stable_node = true`。

### 4. 存档兼容性判定

`save_compatibility_supported` 的公式定义如下：

`save_compatibility_supported = abs(current_data_version - save_data_version) <= supported_version_gap`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| 当前数据版本 | `current_data_version` | int | ≥ 1 | 当前游戏构建所使用的存档数据结构版本 |
| 目标存档版本 | `save_data_version` | int | ≥ 1 | 目标存档所记录的数据结构版本 |
| 支持版本差距 | `supported_version_gap` | int | ≥ 0 | 当前版本可直接兼容或迁移支持的最大版本跨度 |
| 是否受支持 | `save_compatibility_supported` | bool | true / false | 该存档是否仍在当前版本的兼容支持范围内 |

**Output Range:** 布尔值；为 `true` 时可直接读取或迁移，为 `false` 时必须进入不可恢复或人工处理分支。  
**Example:** 若 `current_data_version = 6`、`save_data_version = 5`、`supported_version_gap = 2`，则 `save_compatibility_supported = true`。

### 5. 迁移后有效性判定

`migration_validation_passed` 的公式定义如下：

`migration_validation_passed = migrated_required_fields_present AND migrated_consistency_checks_passed`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| 迁移后必需字段齐全 | `migrated_required_fields_present` | bool | true / false | 迁移后的档案是否补齐了当前版本要求的所有必需字段 |
| 迁移后一致性校验通过 | `migrated_consistency_checks_passed` | bool | true / false | 迁移后的档案是否通过当前版本的一致性复检 |
| 迁移后有效性是否通过 | `migration_validation_passed` | bool | true / false | 该迁移结果是否可以成为新的有效快照 |

**Output Range:** 布尔值；只有为 `true` 时，迁移结果才允许进入恢复流程。  
**Example:** 若迁移后的字段完整且跨系统校验全部通过，则 `migration_validation_passed = true`。

### 6. 存档摘要进度比例

`save_summary_progress_ratio` 的公式定义如下：

`save_summary_progress_ratio = completed_progress_units / max(1, total_progress_units)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| 已完成进度单位 | `completed_progress_units` | float | 0–`total_progress_units` | 当前存档在赛季、阶段或长期主线中的已完成进度单位 |
| 总进度单位 | `total_progress_units` | float | > 0 | 当前存档所属阶段下可用于展示的总进度单位 |
| 存档摘要进度比例 | `save_summary_progress_ratio` | float | 0–1 | 用于存档列表摘要展示的进度比例值 |

**Output Range:** 0–1；主要服务存档摘要和读档前信息展示，不直接驱动玩法结算。  
**Example:** 若某档案当前赛季已完成 `9` 个推进单位，总计 `18` 个单位，则 `save_summary_progress_ratio = 9 / 18 = 0.5`。

### Formula Ownership Notes

- `season_progress_ratio` 不在本系统中重新定义；赛季进度本体由 `design/gdd/time-and-season-progression-system.md` 拥有，本系统只保存和恢复其结果。
- `resource_settlement`、`effective_attribute_value`、`attribute_growth` 不在本系统中定义；本系统只持久化这些共享结果，不拥有它们的业务计算规则。
- 比赛胜负、训练收益、建筑完工收益、声望奖励等内容公式不在本系统中定义；本系统只定义“这些结果在何时视为已确认并可落档”。
- 如果后续系统希望新增跨系统必需字段、改变稳定节点集合、或修改兼容性判定口径，必须先回到本系统修订，而不能在各自 GDD 中静默覆盖。

## Edge Cases

- **If 玩家在 `Match In Progress` 中手动请求保存**: 本次保存不得直接写出标准可恢复快照；系统必须延后到最近稳定节点，或明确阻止保存并告知“当前处于不可安全保存的比赛中途状态”。
- **If 自动保存触发时某个下游系统还没完成本轮结算**: 自动保存必须等待所有必需持久化结果确认完成后再执行；不得把“资源已扣除但奖励未发放”之类的半完成状态写入快照。
- **If `save_snapshot_completeness < 1`**: 本次快照直接判定为无效，不得提交覆盖任何现有有效存档；系统必须保留之前最后一个有效快照。
- **If `cross_system_consistency_ratio < 1`**: 本次保存或迁移结果必须判定失败，并进入 `Recovery`；不得因为“只有一小项不一致”而放行成正式可用档案。
- **If 玩家在一次保存提交过程中关闭游戏或程序异常退出**: 结果必须表现为原子行为——要么新档完整存在，要么旧档完整保留；不得留下一个被 UI 当作正常存档显示、但实际不可读的半写入档案。
- **If 手动保存目标槽位已经存在旧进度**: 系统必须在覆盖前明确提示目标信息；若玩家取消，则必须完整保留原槽位内容，不得对其做任何部分写入。
- **If 玩家尝试删除唯一的有效存档**: 系统必须要求显式确认；若删除成功，后续所有入口都必须把该进度视为不存在，而不是保留悬挂摘要或失效引用。
- **If 读档时发现目标存档缺失关键字段**: 该档案不得直接恢复到世界状态；系统必须优先尝试备份快照或最近有效自动存档，否则明确标记该档不可继续使用。
- **If 读档时发现存档版本低于当前版本但仍在支持跨度内**: 系统必须先执行迁移，再做完整性与一致性复检；迁移未通过前不得进入 `State Restore`。
- **If 读档时发现存档版本超出 `supported_version_gap`**: 该档案必须被标记为不受支持；系统不得尝试“尽量读一部分”，以免恢复出看似能玩但实际错误的世界状态。
- **If 迁移后新增字段需要默认值**: 默认值必须来自当前版本已声明的兼容规则；不得临时猜测或按运行时缓存补值后直接视为正式权威数据。
- **If 最近稳定节点语义与实际快照内容冲突**: 该快照应判定为异常数据；系统必须优先信任完整性校验和一致性结果，并进入恢复或回退流程。
- **If 当前档案记录自己停在 `Match In Progress` 或其他瞬时节点**: 该档案不得作为标准成功读档结果直接恢复；系统必须回退到最近一个已确认稳定节点，或判定该档异常。
- **If 某次赛后结算已经发奖，但存档中未写入对应资源变化**: 这是典型跨系统不一致；系统必须视为校验失败，而不是在读档时再次自动补发，避免重复奖励。
- **If 某次阶段结算完成后立刻触发赛季结算**: 本系统必须保证这两个节点的已确认结果都进入同一一致性快照，或按固定顺序生成可解释的连续稳定快照；不得只落其中一半。
- **If 玩家读档时当前运行世界已有未保存进度**: 系统必须明确提示当前未保存进度将被放弃；只有玩家确认后才能切换到目标档案。
- **If 自动保存与手动保存几乎同时命中同一稳定节点**: 系统必须使用固定优先级或队列顺序处理，避免两个保存流程互相覆盖或生成来源不明的最终快照。
- **If 存档摘要可读，但正文数据损坏**: UI 不能仅凭摘要把它当作正常档案；进入读档时必须以正文校验结果为准，并把该档标记为损坏或需恢复。
- **If 下游系统在读档恢复后尝试用本地缓存覆盖权威值**: 该覆盖必须无效；所有运行时缓存都只能从恢复后的权威快照重新派生。
- **If MVP 阶段尚未实现完整多备份链或复杂云同步**: 系统仍必须至少保证“最后一个有效手动档 + 最近有效自动档”的本地恢复底线，优先满足可靠恢复而不是扩展特性。

## Dependencies

存档与读档系统位于 Foundation 层，是所有长期经营内容的持久化底座。它本身不拥有训练、比赛、建设、经济或赛事的业务规则，但负责把这些系统已经确认的长期状态收束成可校验、可迁移、可恢复的一致性快照。对上，它依赖游戏概念、系统索引、数值系统与时间推进系统来确定“什么必须被长期保留、何时可安全落档”；对下，它为所有会产生长期状态的系统提供统一的保存/恢复边界。

### Upstream Dependencies

| Dependency | Type | Why it matters | Required interface |
|---|---|---|---|
| `design/gdd/game-concept.md` | Hard | 概念文档明确要求长期经营进度可持续、可恢复，并指出存档损坏或升级不兼容时需要版本迁移、验证与恢复策略 | 长期成长目标、资源种类、关键进度对象、兼容与恢复要求 |
| `design/gdd/systems-index.md` | Hard | 定义了本系统在 Foundation/MVP 的位置，以及哪些后续系统会依赖它 | 系统层级、优先级、依赖方向 |
| `design/gdd/balance-system.md` | Hard | 定义了哪些共享数值类别具有长期意义，以及哪些数值结果需要被视为权威状态保存 | 共享资源定义、属性语义、长期数值类别、版本化权威值边界 |
| `design/gdd/time-and-season-progression-system.md` | Hard | 定义了哪些节点是可验证稳定节点、哪些中间态不能直接恢复，以及赛季/阶段语义如何存在 | 稳定节点集合、当前时间轴位置、阶段状态、赛季进度、关键节点恢复语义 |

### Dependency Rules

1. 存档与读档系统提供的是统一持久化边界，不是下游系统业务内容的定义；下游系统可以扩展自己的数据字段，但不能私自绕过本系统写入另一套长期权威状态。
2. 任何下游系统若希望新增“必须持久化”的长期字段、改变保存时机、或把新的中间态声明为可恢复状态，必须先回到本系统修订，而不能在本地 GDD 中静默扩张存档边界。
3. 下游系统可以拥有自己的内容表、运行时缓存、临时 UI 状态和推导值，但必须明确区分哪些属于长期权威数据、哪些属于读档后可重建的派生数据。
4. 当后续 GDD 完成时，依赖关系必须双向成立：本节列出的下游系统，需要在它们各自的 Dependencies 或 Interactions 章节中反向声明“依赖存档与读档系统”。
5. 如果某个系统只展示存档信息而不改变长期状态，则它对本系统属于软依赖；如果某个系统会生成、确认、恢复、迁移或持久化长期状态，则属于硬依赖。
6. 在 MVP 阶段，时间与赛季推进系统、运动员培养系统、比赛竞技系统和经济管理系统是最关键的承接者；它们的状态边界必须优先验证是否能被本系统稳定保存与恢复。
7. 本系统必须优先兼容 Foundation 层已定义的共享语义，尤其是数值系统的权威长期值和时间系统的稳定节点；若这些上游语义变更，本系统必须同步修订，否则下游恢复语义会失真。

## Tuning Knobs

本节仅包含存档与读档系统拥有的共享调参项与可靠性目标，不包含具体球员字段表、赛事表、建设表或经济内容表。它们控制的是保存频率、恢复安全性、兼容跨度和玩家感知成本，而不是下游系统的业务数值。

| 调参项 | 控制内容 | 安全范围 | 调高风险 | 调低风险 | 主要影响 |
|---|---|---|---|---|---|
| 自动保存触发密度 `autosave_trigger_density` | 单位进度内触发自动保存的频率 | 每 `1` 至 `3` 个关键稳定节点一次 | 频繁打断体验、写盘压力上升、摘要更新时间过密 | 玩家丢失进度窗口变大，恢复安全感下降 | 安全感、流畅度 |
| 自动保存保留槽位数 `autosave_slot_count` | 系统保留的最近有效自动存档数量 | `1` 至 `5` 槽 | 占用更多存储并增加管理复杂度 | 恢复回退空间不足，一次损坏可能无后备 | 恢复冗余、容错率 |
| 手动存档槽位上限 `manual_save_slot_cap` | 单个玩家档案允许保留的手动存档数量 | `3` 至 `12` 槽 | 管理负担上升，列表噪音增多 | 玩家保留关键阶段节点的自由度不足 | 玩家掌控感、UI 负担 |
| 保存延后容忍窗口 `save_defer_window_target` | 在瞬时节点发起保存后，允许等待最近稳定节点的目标窗口 | `0` 至 `1` 个关键流程跳转 | 延后过久，玩家误以为已经保存成功 | 过于严格，很多场景下频繁拒绝保存 | 可预期性、易用性 |
| 快照校验项密度 `consistency_check_density` | 每次保存/读档执行的一致性校验项数量 | `8` 至 `20` 项核心校验 | 校验过重，保存/读档等待感增强 | 错误状态更容易漏检，损坏档放行概率上升 | 可靠性、性能感知 |
| 兼容版本跨度 `supported_version_gap` | 当前版本允许直接兼容或迁移的历史版本差距 | `1` 至 `3` 版 | 迁移负担和异常边界变复杂 | 老玩家回流时更易遇到不可恢复档 | 兼容性、维护成本 |
| 恢复回退深度 `recovery_fallback_depth` | 损坏时允许回退检查的最近有效快照层数 | `1` 至 `3` 层 | 恢复链更复杂，错误排查成本上升 | 一旦最近档损坏，成功恢复概率下降 | 容灾能力、实现复杂度 |
| 存档摘要字段密度 `save_summary_field_density` | 存档列表中展示的摘要信息量 | `4` 至 `8` 个核心字段 | 界面噪音变多，选择成本上升 | 信息不足，玩家难以分辨各存档差异 | 可读性、选择效率 |
| 覆盖前确认强度 `overwrite_confirmation_strength` | 覆盖/删档前确认流程的严格程度 | 单次确认至二次高风险确认 | 操作链拖长，频繁覆盖时显得繁琐 | 误删误覆盖风险上升 | 安全感、交互负担 |
| 迁移默认值补齐比例上限 `migration_default_fill_ratio_cap` | 迁移时允许用兼容默认值补齐的字段比例上限 | `0%` 至 `20%` | 迁移看似成功但真实语义失真概率上升 | 稍旧版本档案更容易被直接判死 | 迁移成功率、数据可信度 |
| 读档前未保存警告阈值 `unsaved_progress_warning_threshold` | 当前运行世界累计多少关键变更后必须强化读档覆盖警告 | `1` 至 `3` 次关键长期变更 | 提醒过早过频，形成打扰 | 提醒过晚，玩家更容易误丢进度 | 风险提示、操作信心 |
| 最大可接受保存耗时目标 `save_operation_time_target` | 单次标准保存可接受的目标耗时 | `0.1` 至 `1.0` 秒体感 | 保存卡顿感更强，影响低压力节奏 | 过度压缩流程，可能牺牲校验充分性 | 体感流畅度、完整性 |
| 最大可接受读档耗时目标 `load_operation_time_target` | 单次标准读档可接受的目标耗时 | `0.1` 至 `1.0` 秒体感 | 读档卡顿感增强，破坏“随时回来”的低压力体验 | 过度追求速度，可能牺牲完整性校验或迁移复检充分性 | 体感流畅度、恢复可靠性 |

## Acceptance Criteria

- **GIVEN** 玩家处于 `Planning`、`Post-Match Settlement`、`Stage Settlement`、`Season Settlement` 或其他已声明稳定节点，**WHEN** QA 触发一次手动保存，**THEN** 系统必须成功生成一个完整、可读取、可恢复的有效快照。
- **GIVEN** 玩家处于 `Match In Progress` 或其他未完成结算的瞬时节点，**WHEN** QA 触发一次手动保存，**THEN** 系统必须要么延后到最近稳定节点保存，要么明确拒绝本次保存；不得直接生成标准可恢复档案。
- **GIVEN** 一个有效快照被生成，**WHEN** QA 检查其中的小镇状态、球员状态、资源状态和时间/赛季状态，**THEN** 这些数据必须全部来自同一时间点，不得出现跨系统时序错位。
- **GIVEN** 一个快照缺失任一必需字段，**WHEN** QA 计算 `save_snapshot_completeness`，**THEN** 结果必须小于 `1`，且该快照不得被提交为新的有效存档。
- **GIVEN** 一次保存或迁移后的快照存在跨系统矛盾，**WHEN** QA 计算 `cross_system_consistency_ratio`，**THEN** 结果必须小于 `1`，且系统必须把该结果判定为失败而不是放行为可用档。
- **GIVEN** 当前运行节点属于本系统声明的稳定节点集合，**WHEN** QA 检查 `recoverable_stable_node` 判定，**THEN** 结果必须为 `true`；若节点不在集合内，结果必须为 `false`。
- **GIVEN** 一次保存在提交阶段发生异常中断，**WHEN** QA 重启并检查该槽位与旧槽位状态，**THEN** 最终结果必须表现为原子行为：要么新档完整可用，要么旧档完整保留，不得留下可见的半写入损坏档。
- **GIVEN** 玩家尝试覆盖已有手动存档，**WHEN** QA 执行覆盖流程，**THEN** 系统必须先明确提示目标存档信息；若玩家取消，原档内容必须完全不变。
- **GIVEN** 玩家尝试删除一个有效存档，**WHEN** QA 确认删除，**THEN** 该存档必须从所有可选列表与摘要中移除；未确认前不得发生实际删除。
- **GIVEN** 一个目标存档版本与当前数据版本差距在 `supported_version_gap` 内，**WHEN** QA 计算 `save_compatibility_supported`，**THEN** 结果必须为 `true`，且系统必须进入直接恢复或迁移流程而不是直接拒绝该档。
- **GIVEN** 一个目标存档版本超出 `supported_version_gap`，**WHEN** QA 计算 `save_compatibility_supported`，**THEN** 结果必须为 `false`，且系统必须明确将该档案标记为不受支持。
- **GIVEN** 一个旧版本档案需要迁移后才能读入，**WHEN** QA 完成迁移并检查 `migration_validation_passed`，**THEN** 只有在字段完整且一致性复检通过时，系统才允许进入 `State Restore`。
- **GIVEN** 一个损坏档缺失关键字段或正文数据不可用，**WHEN** QA 尝试读档，**THEN** 系统必须优先尝试最近有效自动档或备份快照；若无恢复项，必须明确提示该档不可继续使用。
- **GIVEN** 一个有效存档记录了最近稳定节点语义，**WHEN** QA 读档恢复，**THEN** 玩家必须返回到与该节点语义一致的可解释入口，而不是回到奖励半领、比赛半开或结算半完成的中间态。
- **GIVEN** 赛后结算已经确认奖励发放，**WHEN** QA 读取该存档并核对资源与奖励标记，**THEN** 系统不得重复补发同一奖励，也不得丢失已确认发放结果。
- **GIVEN** 一次阶段结算与赛季结算连续命中，**WHEN** QA 在该节点后保存并读档恢复，**THEN** 两个节点已经确认的长期结果都必须被正确保留，不得只恢复其中一半。
- **GIVEN** 读档前当前运行世界存在未保存长期变更，**WHEN** QA 尝试载入另一档，**THEN** 系统必须明确警告当前未保存进度将被放弃，且只有在确认后才允许切换。
- **GIVEN** 读档完成后下游系统需要展示属性、资源、建设或赛季信息，**WHEN** QA 检查展示值来源，**THEN** 所有展示都必须来自恢复后的权威快照或其重新派生值，而不是旧缓存反向覆盖。
- **GIVEN** 存档列表展示摘要信息，**WHEN** QA 核对 `save_summary_progress_ratio` 与当前赛季/阶段进度，**THEN** 展示比例必须与公式计算结果一致，并与实际存档进度语义保持一致。
- **GIVEN** MVP 版本尚未实现复杂云同步或长备份链，**WHEN** QA 制造一次最近档损坏场景，**THEN** 系统至少必须能验证“最后一个有效手动档 + 最近有效自动档”的本地恢复底线是否成立。
- **GIVEN** 一次典型玩家会话在正常节奏中推进训练、比赛和结算，**WHEN** QA 采集保存与读档体感样本，**THEN** 自动保存频率、保存耗时和读档耗时必须落在本 GDD 调参目标带内，或明确标记为调优未通过。
