## Overview

联赛与赛事结构系统是《足球小镇》中把单场比赛结果组织成有目标、有进程、有长期追求感的赛季竞技层的结构系统。它不定义单场比赛如何演算——那由比赛竞技系统拥有——而是负责回答"这一场胜利在联赛里值多少分、我的球队排第几、距离晋级还有多远、这个赛季的最终目标是什么"。它把时间系统提供的赛季节奏、比赛系统提供的单场结果包，编排成玩家可追踪的联赛积分榜、晋级/降级路线和赛季终局目标，使每一场比赛都成为更大叙事中的一步，而不是孤立的胜负事件。在 MVP 阶段，联赛与赛事结构系统不需要实现复杂多级联赛网络，但必须至少定义一条从低级别到高级别的可晋级联赛链，让玩家清楚看到"赢下去能走多远"，并验证"单场结果 → 积分排名 → 赛季目标达成"的赛季层闭环是否成立。

## Player Fantasy

联赛与赛事结构系统服务的玩家幻想是："我的球队不止在为一场比赛而战——我们在为一个赛季、一次晋级、一段从小镇走向更大舞台的旅程而战。"玩家期待的不是孤立的一输一赢，而是能看到积分榜上的排名在每一轮之后变化、晋级线在赛季末越来越近（或越来越远）、降级压力在连败时逐渐积累，最终在赛季收官战迎来"赢了就晋级、输了就再来一年"的关键时刻。

这种幻想的核心不是高压竞技的"必须赢"，而是长期经营中的"有目标可追"。每一场比赛的结果都有了上下文——它不是一场无关紧要的胜负，而是积分榜上的一步、晋级路上的一程、球队故事里的一章。联赛与赛事结构系统必须让玩家在多个赛季的跨度中感受到：从底层联赛一路爬上来的成就感，保级成功的释然，以及"下一个赛季我们会更好"的持续期待。它的情感锚点不是某一场关键比赛的紧张，而是"这支小镇球队正在一段可以被讲述的旅程中"。

## Detailed Rules

### Core Rules

1. 联赛与赛事结构系统是赛季层竞技结构的权威来源，负责定义联赛层级、积分规则、排名逻辑、晋级/降级规则、赛季编排以及终局目标语义。它不拥有单场比赛如何演算——比赛结果包由比赛竞技系统产出后，由本系统赋予积分与排名含义。
2. 本系统只拥有"联赛层"的结构与规则，不拥有单场比赛演算、共享属性公式、赛季节奏推进或经济奖励结算：
   - 比赛结果包（胜/平/负、比分、关键事件摘要）由比赛竞技系统拥有；
   - 赛季推进节奏、比赛节点调度、阶段结算时机由时间与赛季推进系统拥有；
   - 共享属性与评分公式由数值系统拥有；
   - 赛季奖励（奖金、资源）的结算语义由经济管理系统拥有。
3. MVP 阶段必须至少定义一条两级联赛链：低级别联赛（起始联赛）和高级别联赛（晋级目标）。不建议 MVP 实现超过三级联赛结构，优先验证晋升闭环的完整性和可感受性，而非复杂度。
4. 每个联赛级别必须拥有以下基本属性：联赛名称、参赛球队数量、赛季比赛总轮次、晋级名额数、降级名额数、对手强度基准区间。
5. MVP 阶段的赛制默认为双循环联赛（每支球队与同联赛其他球队各对战两次，主客场各一）。不要求实现杯赛、淘汰赛或季后赛，但这些模式的结构接口应预留。
6. 积分规则必须简单可预期。MVP 默认采用标准足球积分制：胜 = 3 分，平 = 1 分，负 = 0 分。
7. 联赛排名以积分降序排列。积分相同时，MVP 阶段按以下优先级依次比较打破平局：
   - 净胜球（总进球 - 总失球）；
   - 总进球数；
   - 相互对战成绩（如果两队积分相同）；
   - 若仍无法区分，视为并列排名（MVP 允许并列，不强制实现复杂多级打破规则）。
8. 赛季结束时，排名最高的 N 支球队（N = 晋级名额数）获得晋级资格，下赛季进入上一级联赛；排名最低的 M 支球队（M = 降级名额数）降入下一级联赛。最高级联赛无晋级、最低级联赛无降级。
9. 每轮比赛的对阵由本系统在赛季开始时生成，生成规则必须可预期：双循环赛制下，每支球队与同联赛其他球队各对阵两次，整个赛季的对阵表在赛季初确定且不随中期排名变化而改变。
10. 对手球队的强度不由本系统独立定义。对手强度基准区间用于在联赛系统未完成时生成临时对手数据；当比赛系统消费本系统的对阵表后，具体对手参数由比赛系统从对阵表中解析并使用 `default_opponent_profile` 或联赛系统提供的对手强度参考值生成。
11. 单场结果包由比赛系统产出后，本系统必须消费以下字段来更新联赛状态：比赛 ID、主队、客队、主队进球、客队进球、胜/平/负结果。
12. 联赛积分榜必须在每场比赛结果确认后立即更新。玩家在任意时刻查看积分榜时看到的必须是最新的累积结果，而不是延迟批次更新。
13. 赛季结束条件由时间与赛季推进系统发出赛季结算信号（`season_progress_ratio >= 1`，即赛季推进到终点）。本系统收到赛季结算信号后必须完成：最终积分榜锁定、晋级/降级名单确定、赛季摘要生成。
14. 赛季结算完成后，新赛季的联赛构成必须基于上赛季晋级/降级结果重新确定，并在新赛季首轮比赛前将更新后的联赛分配通知对阵生成模块。
15. 系统必须为玩家提供可随时查阅的赛季信息视图，MVP 最小集包括：当前联赛积分榜、本赛季剩余赛程、历史赛季结果摘要（上一赛季）。
16. 经济管理系统已完成 MVP 设计，其奖金、转播分成、门票收入等赛季奖励结算逻辑不在本系统中定义。本系统负责在赛季结算时输出晋级/降级/排名标签和赛季成绩摘要，供经济系统消费并计算具体奖励。
17. MVP 阶段联赛系统不拥有"球员转会市场""球探网络""青训选拔"等涉及球员来源的跨联赛机制。这些内容属于运动员培养系统或后续 Feature 系统的扩展范畴。
18. MVP 阶段联赛与赛事结构系统的首要目标是验证：玩家在经历一个完整赛季后，能否清楚回答"我排第几、能不能晋级、下赛季在哪个联赛、这个赛季算成功还是失败"。

### States and Transitions

| State | Description | Enter condition | Exit condition | Valid next states |
|---|---|---|---|---|
| Pre-Season | 新赛季开始前的准备状态，确定联赛构成、生成对阵表、展示赛季目标 | 上一赛季结算完成，或新档首次进入 | 玩家确认进入新赛季或对阵表生成完毕 | Season In Progress |
| Season In Progress | 赛季进行中，积分榜随每轮比赛动态更新 | Pre-Season 确认进入 | 赛季最后一轮比赛结果确认，或时间系统发出赛季结算信号 | Season Settlement |
| Season Settlement | 赛季结算，锁定最终积分榜，确定晋级/降级名单，展示赛季摘要 | 赛季最后一轮比赛完成，赛季结算节点触发 | 玩家确认赛季结果 | Pre-Season / Career Review |
| Career Review | 展示多赛季累计成绩、历史晋级轨迹和长期成就（MVP 可为简化视图） | 赛季结算完成，玩家选择查看生涯回顾 | 玩家返回 | Pre-Season / Season In Progress |

### Interactions with Other Systems

| System | 联赛与赛事结构系统提供 | 该系统提供回联赛与赛事结构系统 | Ownership boundary |
|---|---|---|---|
| 比赛竞技系统 | 对阵表（谁 vs 谁、主客场、比赛轮次）、对手强度参考值、比赛重要性标签 | 单场比赛结果包（胜/平/负、比分、关键事件摘要） | 比赛系统定义单场如何演算；联赛系统定义这场比赛在赛季中意味着什么 |
| 时间与赛季推进系统 | 赛季起止标记、轮次结构、赛季结算触发需求 | 赛季推进节奏、比赛节点调度、`season_progress_ratio`、赛季行动窗口预算 | 时间系统定义赛季何时开始/结束；联赛系统定义赛季内部怎么编排 |
| 存档与读档系统 | 积分榜、赛程、晋级/降级名单、赛季摘要等长期联赛状态 | 稳定保存节点定义、快照组装时机、恢复后联赛状态重建语义 | 存档系统定义何时保存/如何恢复；联赛系统定义哪些联赛数据属于长期权威状态 |
| 经济管理系统 | 晋级/降级/排名标签、赛季成绩摘要，供经济系统决定奖金与资源分配 | 赛季奖金、转播分成、门票收入等经济奖励的结算规则 | 经济系统定义奖励多少；联赛系统定义"什么成绩配什么奖励层级" |
| 声望与成就系统 | 晋级里程碑、赛季排名成就、长期竞赛成就的触发条件 | 成就解锁逻辑、声望等级计算（该系统完成后） | 成就系统定义解锁什么；联赛系统定义触发条件 |
| 比赛表现 UI | 积分榜数据、赛程数据、晋级/降级状态、赛季进度信息 | 积分榜视觉呈现、赛程日历展示、晋级线高亮 | 联赛系统定义数据语义；UI 系统定义如何把积分榜和赛程做得一目了然 |
| 主循环 UI 框架 | 赛季信息入口（积分榜、赛程）的导航位置和数据摘要 | 主界面赛季区域的容器和导航规则 | UI 框架定义入口在哪；联赛系统定义入口里显示什么数据 |

> **Economy dependency:** 经济管理系统已完成 MVP 设计。赛季奖励金额由经济系统拥有；本系统只输出赛季结算标签和成绩摘要，作为经济系统计算赛季奖励的输入。

## Formulas

### 1. 积分计算

`league_points = Σ(match_result_points_i)` where `match_result_points_i = 3 for win, 1 for draw, 0 for loss`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 单场结果分 | `match_result_points_i` | int | {0, 1, 3} | 每场比赛贡献的积分 |
| 赛季总积分 | `league_points` | int | 0–(3 × matches_per_season) | 球队赛季累计积分 |

**Output Range:** 0 到 3 × 赛季总轮次。  
**Example:** 一支球队在 20 轮赛季中 10 胜 5 平 5 负 → `league_points = 10×3 + 5×1 + 5×0 = 35`。  
**Ownership:** 本系统完全拥有。

### 2. 胜率换算（展示用）

`season_win_rate = (wins + 0.5 × draws) / max(1, total_matches)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 胜场数 | `wins` | int | ≥ 0 | 赛季获胜场次 |
| 平局数 | `draws` | int | ≥ 0 | 赛季平局场次 |
| 总场次 | `total_matches` | int | ≥ 1 | 赛季已完成的比赛场次 |
| 赛季胜率 | `season_win_rate` | float | 0–1 | 含平局折算的有效胜率 |

**Output Range:** 0–1。  
**Example:** 10 胜 5 平 5 负 → `season_win_rate = (10 + 2.5) / 20 = 0.625`。  
**Ownership:** 本系统完全拥有。

### 3. 排名判定

`rank = order_by(league_points DESC, goal_difference DESC, goals_scored DESC, head_to_head_points DESC)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 净胜球 | `goal_difference` | int | 任意 | 总进球 - 总失球 |
| 总进球 | `goals_scored` | int | ≥ 0 | 赛季总进球数 |
| 相互对战积分 | `head_to_head_points` | int | 0–3 | 仅当两队积分相同时比较 |
| 排名 | `rank` | int | 1–N | 球队在联赛中的排名位置 |

**Output Range:** 1（榜首）到 N（联赛参赛球队数）。  
**Ownership:** 本系统完全拥有。

### 4. 晋级/降级判定

`promotion = (final_rank ≤ promotion_slots) AND (current_tier < highest_tier)`  
`relegation = (final_rank > (team_count − relegation_slots)) AND (current_tier > lowest_tier)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 最终排名 | `final_rank` | int | 1–N | 赛季结束时的最终排名 |
| 晋级名额数 | `promotion_slots` | int | 1–3 | 当前联赛的晋级名额数 |
| 降级名额数 | `relegation_slots` | int | 1–3 | 当前联赛的降级名额数 |
| 联赛参赛队数 | `team_count` | int | 8–20 | 当前联赛的球队总数 |
| 当前联赛层级 | `current_tier` | int | 1–N | 数值越小级别越高 |
| 晋级 | `promotion` | boolean | {true, false} | 球队是否晋级 |
| 降级 | `relegation` | boolean | {true, false} | 球队是否降级 |

**Output Range:** true/false。  
**Example:** 球队在 12 队联赛中排名第 2，`promotion_slots = 2` → `promotion = true`。排名第 11，`relegation_slots = 2` → `relegation = true`。  
**Ownership:** 本系统完全拥有。

### 5. 每队赛季场次

`matches_per_team_per_season = 2 × (team_count − 1)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 联赛参赛队数 | `team_count` | int | 8–20 | 当前联赛的球队总数 |
| 每队赛季场次 | `matches_per_team_per_season` | int | ≥ 0 | 双循环赛制下每支球队的总比赛场次 |

**Output Range:** 14（8 队）到 38（20 队）。  
**Example:** 12 队联赛 → `matches_per_team_per_season = 2 × 11 = 22` 场。  
**Ownership:** 本系统完全拥有。

### Formula Ownership Notes

- 积分、排名、晋级/降级的判定逻辑完全由本系统拥有；任何下游系统（比赛表现 UI、声望与成就系统、经济管理系统）如需引用这些结果，应从本系统的输出接口消费。
- `goal_difference` 和 `goals_scored` 的原始数据来自比赛系统产出的单场结果包。
- 对阵生成算法的具体实现（蛇形排列、循环轮转等）属于程序实现细节，不在本节作为设计级公式定义。
- 经济系统接入后，如需要对晋级/降级附加奖金倍率或特殊奖励逻辑，应在本系统的奖励接口上扩展，而不是在联赛系统中直接定义金额。

## Edge Cases

- **If 新档首次进入且没有任何历史赛季数据**: 系统必须将球队置入最低级别联赛，生成首个赛季对阵表，并在 Pre-Season 展示"第一个赛季"的起始状态，不得尝试读取不存在的历史数据导致空引用。
- **If 赛季最后一轮出现多队积分完全相同且打破规则全部耗尽后仍无法区分**: 系统必须允许并列排名，并在并列涉及晋级/降级名额时明确标记"并列第 N 名"；不得随机挑选晋级/降级球队或进入死循环。
- **If 一支球队晋级后新赛季阵容因球员流失严重弱于高级别联赛对手基准**: 系统应将此视为正常玩法结果（"升班马困境"），不得自动补强球队或降低对手强度以"保护"玩家。
- **If 一支球队降级后新赛季实力远超低级别联赛对手基准**: 系统应将此视为正常玩法结果（"降维打击"反弹），不得自动削弱球队或提升对手以制造人为难度。
- **If 赛季进行中比赛系统返回了一场异常结果（如双方进球数均为负数或超过合理上限）**: 该场比赛结果应被标记为需要复核，积分榜先不更新该场，同时通知比赛系统数据异常；不得将错误数据静默写入积分榜。
- **If 赛季进行中时间系统因异常提前触发了赛季结算信号（如赛季未完成就触发结算）**: 联赛系统必须拒绝结算请求，并将赛季状态和未完成轮次报告给时间系统，不得用不完整数据生成最终积分榜。
- **If 同一场比赛的结果被重复提交（如比赛系统多次回传同一比赛 ID）**: 联赛系统必须检测重复并以首次提交的结果为准；后续重复提交的记录应被丢弃并记录异常。
- **If 球队数量在赛季进行中发生异常变化（如对手被移除导致联赛参赛队数不等于赛季初始值）**: 该赛季应标记为异常赛季，已完成的比赛积分保留，未完成的比赛标记为取消；赛季结算时系统必须明确说明异常原因。
- **If 最高级联赛的冠军球队没有晋级空间**: 系统应给予"联赛冠军"荣誉标签而非晋级提示；不得错误触发晋级逻辑或显示空晋级目标。
- **If 最低级联赛的垫底球队没有降级空间**: 系统应给予"保级失败——留在最低级联赛"的合理反馈；不得错误触发降级逻辑或显示不存在的下级联赛。
- **If 晋级名额数大于高级别联赛的降级名额数（如 3 支晋级但只有 2 支降级导致上级联赛膨胀）**: MVP 阶段采用对等原则——晋级名额数必须等于上级降级名额数，联赛参数配置时必须校验对等性；若发现不对等，系统应拒绝生成赛季。
- **If 玩家在同一赛季内反复查看积分榜而排名未变化**: 积分榜显示不变是正常行为；系统不需要每次添加"无变化"提示，但排名发生变化时应给出视觉提示（如升降箭头）。
- **If MVP 阶段只有两级联赛且玩家连续降级到最低级后再次垫底**: 球队留在最低级联赛，系统应正常显示"未降级（已是最低级联赛）"，不得崩溃或展示空白降级信息。
- **If 玩家从最低级联赛一路晋级到最高级并夺冠**: 这是正常的终极成就路径——系统应在 Career Review 中展示完整晋级轨迹，并将顶级联赛冠军标记为重大里程碑以供后续成就系统消费。
- **If 经济奖励结算在赛季结算时暂时失败**: 赛季结算时晋级/降级/排名标签和赛季成绩摘要仍正常输出，联赛状态更新不回滚；系统保留待结算标签供经济系统恢复后补结算，并向玩家显示奖励待结算状态。
- **If 一赛季的比赛场次过多导致时间系统的行动窗口不够用**: MVP 阶段联赛参赛队数应控制在合理范围（建议 8–12 队），避免赛季过长；联赛配置的 `team_count` 必须与时间系统的赛季行动窗口预算协同确定。
- **If 杯赛/淘汰赛/季后赛模式在本系统预留但 MVP 未实现**: 对阵生成模块仅处理双循环联赛；预留的赛事类型字段默认为 `league`，其他赛事类型在后续扩展时不需重构联赛核心公式。
- **If 玩家在赛季结算后立即退出游戏未保存赛季结果**: 赛季结算结果和晋级/降级名单必须在结算确认时立即写入联赛长期状态，等待最近稳定存档节点落盘，而不是仅在内存中维持并等待退出时保存。
- **If 多个赛季跨越后历史数据累积过多**: MVP 阶段只要求保留上一赛季的完整数据和 Career Review 摘要；超过保留范围的历史数据可被归约为摘要统计，不需要保留逐场明细。
- **If 下游系统（如声望与成就系统）在赛季结算前请求尚未锁定的排名数据**: 联赛系统必须返回"赛季未结束，排名可能变化"的标记状态，而不是返回当前积分榜快照并让下游误以为是最终结果。

## Dependencies

联赛与赛事结构系统位于 Feature/MVP 层，是《足球小镇》从单场比赛走向赛季征程的竞技组织层。它承接比赛系统产出的结果包和时间系统定义的赛季节奏，将它们编排为积分榜、排名和晋级/降级结构，并为下游 UI、经济、成就和引导系统提供赛季层的结构化数据。

### Upstream Dependencies

| Dependency | Type | Why it matters | Required interface |
|---|---|---|---|
| `design/gdd/game-concept.md` | Hard | 概念文档将"比赛竞技"定义为核心双循环之一，联赛是比赛的长期组织形式 | 核心幻想、长期经营基调、低压力节奏 |
| `design/gdd/systems-index.md` | Hard | 定义了本系统在 Feature/MVP 的位置及依赖方向 | 系统层级、优先级、上下游系统列表 |
| `design/gdd/balance-system.md` | Hard | 不直接消费共享公式，但联赛参数（参赛队数、晋级名额）的数值配置应与其共享数值边界协调；对手强度区间消耗数值系统的输出范围 | 数值边界、属性分段逻辑 |
| `design/gdd/time-and-season-progression-system.md` | Hard | 提供赛季起止时机、轮次调度、比赛节点节奏和赛季结算触发信号 | `match_trigger_reached`、`season_progress_ratio`、赛季行动窗口预算 |
| `design/gdd/save-and-load-system.md` | Hard | 联赛积分榜、赛程、晋级/降级名单属于长期状态，必须随存档一起持久化；赛季结算结果需在稳定节点落档 | 稳定保存节点定义、快照组装接口、恢复后联赛状态重建 |
| `design/gdd/match-competition-system.md` | Hard | 提供每场比赛的标准化结果包，作为积分榜更新的唯一数据来源 | 比赛结果包（胜/平/负、比分、比赛 ID、主客队标识）、对手强度参考值 |
| `design/gdd/economy-management-system.md` | Hard | 赛季结算时需输出晋级/降级/排名标签和赛季成绩摘要供经济系统决定奖励 | 赛季奖励结算规则；本系统只输出标签和摘要，不定义金额 |
| 声望与成就系统 | Soft | 晋级里程碑、赛季排名成就等触发条件由本系统提供 | 成就解锁逻辑——该系统未设计，本系统只输出触发条件 |

| 主循环 UI 框架 | Hard | 赛季信息入口的导航数据、积分榜摘要、赛季进度指示 | 必须声明其 Schedule 视图和赛季摘要区域展示本系统输出的数据 |
| `design/gdd/economy-management-system.md` | Hard (回传) | 晋级/降级/排名标签、赛季成绩摘要 | 必须声明其奖励结算逻辑如何消费本系统的赛季结算标签 |
| 声望与成就系统 | Hard | 晋级里程碑、冠军标记、连胜/连败赛季记录 | 必须声明其成就触发条件依赖本系统的赛季事件标记 |
| `design/gdd/onboarding-system.md` | Soft | 联赛层级概念、赛季结构和晋级/降级说明供引导系统向新玩家解释 | 必须声明引导步骤中联赛概念解释消费本系统的赛季结构定义 |
| 多周目与挑战模式系统 | Soft | 生涯总赛季数、历史晋级轨迹、最高联赛级别记录 | 必须声明其周目继承逻辑如何消费本系统的生涯摘要数据 |

### Dependency Rules

1. 联赛与赛事结构系统负责"单场结果在一季联赛中值多少分、最终排名如何、能否晋级"，不负责"单场怎么踢""赛季什么时候结束""冠军发多少钱"；这些边界分别服从比赛系统、时间系统和经济系统。
2. 任何下游系统若希望新增联赛级别、改变积分规则、修改晋级/降级判定或新增赛事类型，必须先回到本系统修订，而不能在本地 GDD 静默覆盖。
3. 比赛表现 UI 是 MVP 阶段最关键的承接者；它必须基于本系统定义的积分榜结构、排名规则和赛季状态来呈现积分榜和赛程。
4. 经济管理系统是本系统的 Hard 上下游依赖：本系统输出晋级/降级/排名标签和赛季成绩摘要，经济系统消费这些标签计算赛季奖励；声望与成就系统完成后也应在其 GDD 的 Dependencies 中反向声明对本系统的依赖。
5. 时间系统定义了"赛季何时开始与结束"，本系统定义了"赛季内部如何编排"。如果赛季长度或比赛频率需要调整，必须同时回到时间系统和本系统进行协调修改。

## Tuning Knobs

本节仅包含联赛与赛事结构系统拥有的共享调参项。它们控制的是"联赛规模、晋级/降级节奏、赛季长度和竞争张力"，不包含具体奖金金额、比赛演算参数或 UI 布局。

| 调参项 | 控制内容 | 安全范围 | 调高风险 | 调低风险 | 主要影响 |
|---|---|---|---|---|---|
| 联赛参赛队数 `team_count` | 单级别联赛的参赛球队总数 | 8–20 | 队数过多 → 赛季过长，节奏拖沓 | 队数过少 → 赛季太短，联赛进程缺乏积累感 | 赛季长度、赛程密度 |
| 联赛层级数 `tier_count` | 从最低到最高的联赛层级数量 | MVP: 2–3; Full: 2–6 | 层级过多 → 晋级路线太长，终极目标过远 | 层级过少 → 晋级空间不足，长期追求感薄弱 | 长期目标感、生涯跨度 |
| 晋级名额 `promotion_slots` | 每赛季每个联赛的晋级名额数 | 1–3 | 晋级太容易 → 快速升顶后失去目标 | 晋级太难 → 长年卡在同一级别，挫败感积累 | 晋级节奏、赛季成就感 |
| 降级名额 `relegation_slots` | 每赛季每个联赛的降级名额数 | 1–3 | 降级压力过大 → 低压力体验被破坏 | 无降级 → 垫底无后果，赛季失去张力 | 保级压力、赛季戏剧性 |
| 胜/平/负积分值 `points_win` / `points_draw` / `points_loss` | 单场比赛结果对应的积分 | 胜 3 / 平 1 / 负 0 | 胜和平差距过大 → 鼓励过度进攻；过小 → 平局太多 | 改变积分结构会从根本上改变联赛策略行为 | 积分策略、比赛意义 |
| 对手强度基准区间 `opponent_strength_band` | 各级别联赛对手 `team_match_strength` 的默认生成区间 | 低级 30–50; 中级 45–65; 高级 60–85 | 区间过窄 → 级别间差异不明显，晋级感受弱 | 区间跨度过大 → 晋级后实力断崖 | 联赛难度梯度、晋级感受 |
| 赛季结算保留赛季数 `historical_season_retention` | Career Review 和历史记录中保留的完整赛季数据量 | 1–5 个赛季 | 保留过多 → 存储与展示负担增加 | 保留过少 → 长期轨迹感受弱 | 生涯回顾深度 |
| 新人起始联赛 `starting_tier` | 新档开始时的默认联赛级别 | 最低级 | 起始过高 → 失去向上攀升空间 | 起始过低但只有一级 → 无晋升空间 | 初期目标感、生涯起始体验 |
| 晋级/降级名额对等校验 `promotion_relegation_symmetry` | 上级降级名额是否必须等于下级晋级名额 | 对等模式（强制）/ 弹性模式 | 弹性模式 → 联赛规模会逐渐漂移，需额外收缩规则 | 对等模式 → 限制了非对称联赛结构的可能性 | 联赛构成稳定性 |
| 杯赛扩展预留 `cup_tournament_slots` | 为后续杯赛/淘汰赛模式预留的赛事类型槽位 | 0–2 | — | — | 扩展性 |

## Acceptance Criteria

- **GIVEN** 新档首次进入联赛系统，**WHEN** QA 检查联赛状态，**THEN** 球队必须被置入最低级别联赛，且本赛季对阵表已完整生成（每队与其他队各两场、主客场明确）。
- **GIVEN** 比赛系统回传一场结果包（主队 2–1 客队），**WHEN** QA 检查积分榜更新，**THEN** 主队积分 +3、客队积分不变，且两队净胜球和总进球数正确更新。
- **GIVEN** 比赛系统回传一场平局结果包（1–1），**WHEN** QA 检查积分榜更新，**THEN** 双方各 +1 分，净胜球不变，总进球各 +1。
- **GIVEN** 赛季中期有多场比赛结果已确认，**WHEN** QA 检查积分榜排名，**THEN** 排名严格按积分 → 净胜球 → 总进球 → 相互对战顺序排列。
- **GIVEN** 赛季最后一轮完成且时间系统发出赛季结算信号，**WHEN** QA 检查赛季结算，**THEN** 最终积分榜锁定、晋级名单和降级名单正确生成，且晋级/降级名额数符合联赛配置。
- **GIVEN** 球队在低级别联赛赛季结束时排名进入晋级区，**WHEN** QA 进入新赛季，**THEN** 该球队出现在上一级联赛的新赛季参赛名单中。
- **GIVEN** 球队在联赛赛季结束时排名进入降级区，**WHEN** QA 进入新赛季，**THEN** 该球队出现在下一级联赛的新赛季参赛名单中。
- **GIVEN** 最高级联赛冠军产生，**WHEN** QA 检查晋级逻辑，**THEN** 系统不得错误触发晋级或显示空晋级目标；应正常授予联赛冠军标签。
- **GIVEN** 最低级联赛垫底球队产生，**WHEN** QA 检查降级逻辑，**THEN** 系统不得错误触发降级或显示不存在的下级联赛；应正常提示"留在最低级联赛"。
- **GIVEN** 赛季结算完成后新赛季对阵表生成，**WHEN** QA 验证对阵表，**THEN** 每队与其他同联赛球队各对阵两次（主客场各一），且对阵表不包含已降级或已晋级的球队。
- **GIVEN** 赛季最后一轮出现多队积分完全相同且打破规则耗尽后仍无法区分，**WHEN** QA 检查排名结果，**THEN** 系统允许并列排名，且涉及晋级/降级名额时明确标记"并列第 N 名"。
- **GIVEN** 赛季尚未完成但时间系统异常提前触发赛季结算信号，**WHEN** QA 检查联赛系统响应，**THEN** 联赛系统拒绝结算并将赛季状态和未完成轮次报告出来。
- **GIVEN** 同一比赛 ID 的结果被重复提交，**WHEN** QA 检查积分榜，**THEN** 只计首次提交的结果，重复提交被丢弃且不造成积分重复累积。
- **GIVEN** MVP 阶段配置为两级联赛，**WHEN** QA 检查晋降级名额对等性，**THEN** 下级晋级名额必须等于上级降级名额，配置不对等时系统拒绝生成赛季。
- **GIVEN** 玩家随时查看积分榜，**WHEN** QA 在比赛结果确认前后对比查看，**THEN** 积分榜在比赛结果确认后立即更新，排名变化时有视觉变化提示（如升降箭头）。
- **GIVEN** 经济奖励结算接口暂时失败，**WHEN** QA 检查赛季结算过程，**THEN** 晋级/降级/排名标签和赛季成绩摘要正常输出，联赛结算不回滚，并保留待结算标签供经济系统恢复后补结算。
- **GIVEN** 多个赛季跨越后历史数据累积，**WHEN** QA 检查存储与展示，**THEN** 只保留上一赛季完整数据和 Career Review 摘要，超范围的逐场明细可被归约。
- **GIVEN** 玩家在赛季结算后立即退出未保存，**WHEN** QA 重新加载存档，**THEN** 赛季结算结果和晋级/降级名单已持久化，不丢失。
- **GIVEN** 下游系统在赛季中请求排名数据，**WHEN** QA 检查返回结果，**THEN** 联赛系统返回"赛季未结束，排名可能变化"的标记状态，不返回可能误导的临时快照。
- **GIVEN** 玩家从最低级联赛一路晋级到最高级并夺冠，**WHEN** QA 检查 Career Review，**THEN** Career Review 展示完整晋级轨迹，并将顶级联赛冠军标记为重大里程碑。
