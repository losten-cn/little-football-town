## Overview

比赛表现 UI 是《足球小镇》中把单场比赛的赛前、赛中、赛后数据转化为玩家可观看、可操作、可复盘的完整比赛界面的 Presentation 层系统。它不定义比赛如何演算、积分如何累积、排名如何变化——这些由比赛竞技系统和联赛与赛事结构系统拥有——而是负责回答"赛前我的阵容是什么样、比赛中发生了什么、为什么赢了或输了、球员表现怎么样"。它承接主循环 UI 框架定义的 Match Pre、Match Live 和 Match Result 三个容器与导航规则，在框架内完成赛前阵容/战术展示、赛中关键事件流与比分呈现、赛后结果摘要与复盘原因可视化，确保玩家在经历一场比赛时始终知道正在发生什么、为什么会这样、以及这场比赛在赛季中意味着什么。在 MVP 阶段，比赛表现 UI 的首要目标是验证玩家能否在观看一场比赛的过程中产生"看懂了""有悬念""知道为什么"的完整体验。

## Player Fantasy

比赛表现 UI 服务的玩家幻想是："我在场边看着我的球队踢球，我知道正在发生什么、我理解为什么会这样、我感受到了比赛的起伏。"它不是一套数据报表，而是一场有叙事感的比赛观看体验——赛前看到自己精心安排的阵容和战术准备就绪，赛中看到关键事件依次展开、比分变化带来紧张与期待，中场时有机会做出调整扭转局面，赛后则能复盘这场比赛的胜负关键并看到球员的个人表现。

这种幻想的参考是那种让人"看得进去"的体育比赛直播：不需要玩家实时操作每一个动作，但关键节点必须有清晰的反馈，比分变化必须有分量，结果揭晓时必须有情绪。比赛表现 UI 的核心情感锚点不是"操作感"，而是"投入感"和"可理解感"——让一场系统演算出的比赛在玩家眼中变成一段他愿意注视、能理解、会记住的比赛故事。低压力基调在这里体现为：输了不是世界末日，但你必须知道为什么输；赢了固然开心，但更开心的是你清楚自己赛前的哪些选择起了作用。

## Detailed Rules

### Core Rules

1. 比赛表现 UI 是单场比赛各阶段数据的可视化层，负责定义赛前准备界面、赛中反馈界面和赛后结果界面的布局、交互与视觉呈现规则。它不拥有任何比赛数据语义——所有展示内容的含义由比赛竞技系统和联赛与赛事结构系统拥有。
2. 本系统只拥有"比赛信息如何呈现"层面的规则，不拥有比赛演算逻辑、积分排名规则、阵容合法性判定或赛后成长结算：
   - 比赛流程、阵容/战术、关键事件、胜负判定、赛后标签由比赛竞技系统拥有；
   - 积分、排名、联赛上下文、赛季意义由联赛与赛事结构系统拥有；
   - 导航规则、屏幕容器结构、信息刷新触发由主循环 UI 框架拥有。
3. 本系统必须嵌入主循环 UI 框架定义的 Match Pre、Match Live 和 Match Result 三个容器内，不创建独立于框架之外的比赛查看入口。
4. **赛前界面（Match Pre 容器内）** MVP 必须至少展示以下内容：
   - 比赛上下文：对手名称、主/客场标识、比赛轮次、联赛积分榜位置（双方当前排名）；
   - 阵容确认区：当前首发名单、各球员位置、关键球员的状态标签；
   - 战术选择区：可选战术方案、当前选定战术及其简要说明；
   - 阵容/战术修改入口：允许玩家在赛前调整首发和战术；
   - 开赛确认按钮：阵容满足最低合法条件时可用，否则显示具体缺失原因。
5. **赛中界面（Match Live 容器内）** MVP 必须至少展示以下内容：
   - 实时比分：主客双方当前进球数，比分变化时应有视觉强调；
   - 比赛时间/阶段指示：上半场/下半场/伤停补时，当前进行到哪个阶段；
   - 关键事件流：按时间顺序展示比赛中的关键事件（进攻、射门、进球、防守、战术调整生效等）；
   - 中场调整入口：上半场结束时，允许进入 Halftime Adjustment 进行人员或战术调整。
6. 赛中关键事件必须以时间线方式呈现，最新事件在最上方或最显眼位置。每个事件至少包含：发生时间（比赛分钟数）、事件类别图标、简要文字描述。进球事件必须有更显著的视觉呈现。
7. 比分变化必须以醒目的方式呈现，不得与普通关键事件使用相同视觉权重。
8. 上半场和下半场之间必须有明确的中场分隔线或阶段切换提示，使玩家清楚感知到上半场已结束、下半场即将开始。
9. **赛后界面（Match Result 容器内）** MVP 必须至少展示以下内容：
   - 终场比分（最显眼位置）；
   - 胜负原因标签（来自比赛系统的复盘原因组）；
   - 关键事件回看：本场比赛所有关键事件的可滚动时间线；
   - 球员表现摘要：出场球员的评分、关键数据（进球/助攻如有）；
   - 联赛影响提示：本场结果对积分榜位置的影响（来自联赛系统）；
   - 确认按钮：确认结果后返回主界面。
10. 赛中界面不得允许玩家在任何情况下直接退出比赛而不确认——这是主循环 UI 框架与比赛系统的协同规则，本系统负责实现"比赛进行中离开需警告"的交互层。
11. 赛前、赛中、赛后的界面切换必须流畅自然，不使用全屏黑过渡或长时间加载转场。MVP 允许简单过渡动画（时长遵循主循环 UI 框架的 `screen_transition_duration_ms`）。
12. 所有来自比赛系统的数据更新（比分变化、关键事件）必须在 UI 上即时反映，不得延迟批量刷新。
13. 关键事件的时间线在 MVP 阶段不要求可交互（点击展开详情），但必须可滚动查看全部事件。
14. 中场调整界面中，玩家进行的任何修改（阵容调整、战术变更）必须在下半场开始前锁定，并明确提示"调整已生效，下半场即将开始"。
15. 赛后界面中的"联赛影响提示"由联赛系统提供数据。若联赛系统返回的是"赛季未结束，排名可能变化"标记状态，本系统必须展示当前积分榜位置并附该标记，而不是展示可能误导的"已锁定"信息。
16. 赛前界面的对手信息中，对手强度以可读的对比形式呈现（如"对手略强于我们""实力相当""我们是优势方"），而不是直接展示对手 `team_match_strength` 裸数值让玩家自行解读。
17. 赛中界面 MVP 不要求实时动画或比赛画面模拟，但关键事件的呈现必须有节奏感——事件之间有时间流逝的视觉暗示，而不是所有事件瞬间堆出。
18. MVP 阶段比赛表现 UI 不拥有"赛后集锦回放""3D 比赛画面""解说文本"等功能。这些属于后续 Beta 或 Full Vision 阶段的可选扩展。
19. MVP 阶段比赛表现 UI 的首要目标是验证：玩家在经历一场完整比赛（赛前→上半场→中场→下半场→赛后）后，能否回答"发生了什么、为什么会这样、我赛前哪些选择影响了结果"。

### States and Transitions

比赛表现 UI 的状态在主循环 UI 框架的 Match Pre、Match Live 和 Match Result 容器之内。

| State | Description | Parent container | Valid interactions |
|---|---|---|---|
| Match Pre View | 赛前信息展示，包括对手、联赛上下文、阵容确认、战术选择 | Match Pre | 调整首发/位置、切换战术、查看对手信息、确认开赛 |
| Match Live - First Half | 上半场关键事件流与实时比分展示 | Match Live | 观看关键事件流、查看实时比分 |
| Match Live - Halftime | 中场调整界面 | Match Live → Halftime Adjustment | 调整阵容/战术、查看上半场摘要、确认进入下半场 |
| Match Live - Second Half | 下半场关键事件流与实时比分展示 | Match Live | 观看关键事件流、查看实时比分 |
| Match Result View | 终场结果、关键事件回看、球员表现、联赛影响、复盘原因 | Match Result | 滚动查看事件时间线、查看球员评分、确认结果返回 Home |

### Interactions with Other Systems

| System | 比赛表现 UI 提供 | 该系统提供回比赛表现 UI | Ownership boundary |
|---|---|---|---|
| 比赛竞技系统 | 赛前阵容/战术的可视化编辑、赛中关键事件的叙事化呈现、赛后结果的复盘展示 | 比赛状态机、`team_match_strength`、关键事件流、比赛结果包、`post_match_growth_tag`、`player_performance_score`、复盘原因标签 | 比赛系统定义数据语义；比赛表现 UI 定义如何让玩家"观看"和"感受"一场比赛 |
| 联赛与赛事结构系统 | 赛前联赛上下文展示、赛后积分榜影响提示 | 双方当前排名、联赛轮次、主客场标识、积分榜位置 | 联赛系统定义比赛在赛季中的意义；比赛表现 UI 定义如何向玩家传达这个意义 |
| 主循环 UI 框架 | Match Pre / Match Live / Match Result 三个容器内的完整页面实现 | 容器规范、导航规则、`screen_transition_duration_ms`、视觉容器分区 | UI 框架定义在哪里展示；比赛表现 UI 定义展示什么 |
| 运动员培养系统 | 赛前阵容中球员属性的可视化展示 | 球员当前属性、状态标签、位置适配倾向 | 培养系统定义球员数据；比赛表现 UI 在赛前阵容中展示球员状态 |
| 音频系统 | 进球、关键扑救、逆转、终场等关键事件触发时机 | 音效/BGM 呈现与情绪强化（该系统完成后） | 比赛表现 UI 定义"何时触发"高情绪音频事件；音频系统定义"触发什么声音" |

> **Provisional assumption:** 音频系统尚未设计完成，赛中界面预留关键事件音频触发锚点但 MVP 不实现音频集成。

## Formulas

比赛表现 UI 是 Presentation 层系统，不拥有数学公式。本节定义的是比赛界面各阶段的结构规则——它们是赛前、赛中、赛后界面在布局和呈现时必须遵守的约束公式。

### 1. 赛前对手强度可读化

`opponent_strength_label = classify_strength_diff(self_team_match_strength, opponent_team_match_strength)`

**定义：** 将双方队伍强度数值差转化为玩家可直观理解的强度标签。

**Classification Table:**

| Strength diff (self − opponent) | Label |
|---|---|
| ≥ +10 | "我们是优势方" |
| −10 to +10 | "实力相当" |
| ≤ −10 | "对手略强于我们" |

**Ownership:** 本系统完全拥有。`team_match_strength` 由比赛竞技系统提供。

### 2. 关键事件视觉权重

`event_visual_weight = get_event_weight(event_category)`

**定义：** 不同类别关键事件在时间线中的视觉权重分级。

**Weight Table:**

| Event category | Visual weight | Presentation rule |
|---|---|---|
| 进球 | 高 | 比分旁闪烁 + 时间线中显著卡片 + 比分变化动画 |
| 射门/扑救 | 中 | 时间线中标准卡片 |
| 进攻推进/防守 | 低 | 时间线中紧凑条目 |
| 战术调整生效 | 中 | 带战术图标的标准卡片 |
| 体能/状态下滑 | 低 | 紧凑条目 + 球员状态标签更新 |

**Ownership:** 本系统完全拥有。

### 3. 赛后信息区展示优先级

`post_match_section_order = [final_score, reason_tags, event_timeline, player_performance, league_impact, confirm_action]`

**定义：** 赛后结果界面各信息区的固定从上到下展示顺序。

| Order | Section | Content |
|---|---|---|
| 1 | 终场比分 | 主客双方比分，最大字号 |
| 2 | 胜负原因标签 | 来自比赛系统的复盘原因组 |
| 3 | 关键事件时间线 | 本场全部关键事件，可滚动 |
| 4 | 球员表现摘要 | 出场球员评分与关键数据 |
| 5 | 联赛影响提示 | 来自联赛系统的积分榜影响 |
| 6 | 确认按钮 | 返回主界面 |

**Ownership:** 本系统完全拥有。

### 4. 赛中事件节奏

`event_interval_visual = max(min_event_display_interval, base_interval / intensity_factor)`

**定义：** 比赛中关键事件之间的最小视觉呈现间隔，确保事件不瞬间堆出。

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 最小显示间隔 | `min_event_display_interval` | ms | 500–1000 | 任意两个事件展示之间的最小间隔 |
| 基础间隔 | `base_interval` | ms | 1500–3000 | 标准节奏下的基础事件间隔 |
| 强度因子 | `intensity_factor` | float | 0.8–1.2 | 来自比赛系统的比赛强度因子 |
| 实际事件间隔 | `event_interval_visual` | ms | ≥ 500 | 事件动画或展示使用的时间间隔 |

**Output Range:** ≥ 500ms。  
**Ownership:** 本系统完全拥有。

### Formula Ownership Notes

- 本节所有规则属于比赛界面可视化层面的约束，不定义具体像素、颜色、字体或动画参数——这些属于视觉设计规范的范畴。
- 关键事件视觉权重定义了"不同事件在界面上的相对重要性"，但具体卡片样式、图标和动画由视觉实现决定。
- 赛后信息区优先级定义了区域顺序，但每区的具体布局由视觉实现决定。

## Edge Cases

- **If 赛前界面加载时对手数据尚未就绪**: 对手信息区展示"对手数据加载中"占位状态，开赛确认按钮禁用，不展示空对手名称或错误默认值。
- **If 赛前阵容无可出场球员（全员伤病/不可用）**: 阵容确认区展示空阵容占位提示并列出原因；开赛按钮禁用并显示"无可用球员，无法开赛"。
- **If 玩家反复切换战术方案但未确认开赛**: 允许无限切换预览且响应无延迟累积；退出赛前界面后不锁定战术，下次进入时恢复最近一次选择。
- **If 关键球员同时携带多个状态标签（如"疲劳"+"轻伤"+"士气低落"）**: 所有标签同时可见，不互相覆盖或截断；超出显示容量的标签以"+N"折叠方式呈现，可点击展开。
- **If 赛中关键事件在短时间内连续涌入（如进球 → 射门 → 战术调整几乎同时发生）**: 每个事件遵守 `event_interval_visual` 最小间隔依次呈现，不瞬间堆出也不丢失事件。
- **If 一场比赛产出事件数达到 `max_events`（15）且超出可视区**: 时间线支持滚动查看全部事件，最新事件默认可见；不因数量多而压缩单个事件呈现尺寸至不可读。
- **If 上半场结束比分 0–0（无进球）**: 中场分隔线和高亮仍正常展示，调整入口正常可用；上半场摘要注明"双方均无建树"，不因无进球而跳过中场阶段。
- **If 玩家在中场调整界面未做任何修改直接确认**: 视为合法选择，直接沿用上半场阵容/战术进入下半场；不弹出"你未做调整"等不必要的二次确认。
- **If 玩家在中场调整中修改了阵容但未确认就返回**: 弹出确认对话框"放弃本次调整？"；直接返回保留原阵容，修改静默丢失。
- **If 下半场结束前比分短时间多次变化（如 85' 扳平、90' 绝杀）**: 每次比分变化独立触发变化动画，后续变化排队展示；不因前次动画未播完而跳过后续；赛后时间线可回看所有变化。
- **If 赛后全体球员的 `post_match_growth_tag` 均为"无"**: 球员表现摘要区仍正常展示评分和出场时间；"无成长"是合法结果，不隐藏或压缩该区域。
- **If 联赛系统尚未完成（provisional），赛后联赛影响区需展示数据**: 展示当前积分榜快照并附带"赛季未结束，排名可能变化"标记，不隐藏该区域。
- **If 赛后复盘原因标签同时命中多个原因**: 所有命中原因同时展示，按比赛系统定义的优先级排序，不只展示第一个或随机选择。
- **If 对手强度差值恰好在分类边界（±10 或 0）**: +10 → "我们是优势方"；-10 → "对手略强于我们"；0 → "实力相当"；不得因浮点精度问题导致边界抖动。
- **If 玩家未滚动查看赛后完整时间线就直接点击确认返回**: 允许直接确认，阅读时间线是可选操作而非阻塞步骤。
- **If 比分变化动画播放时设备性能波动导致帧率下降**: 动画可掉帧但不阻塞事件时间线渲染；动画超时后直接展示最终比分状态，不无限等待。
- **If 屏幕切换过渡时长在主循环 UI 框架的边界值（150ms / 400ms）**: 过渡在给定时长内完成，150ms 无割裂感，400ms 无明显拖沓感；过渡期间不出现白屏、黑屏或残留内容。
- **If 设备在 Match Live 期间收到系统中断（来电、低电量等）**: 本系统不做特殊处理，恢复后刷新当前比赛状态即可；暂停/恢复逻辑由 UI 框架和比赛系统协同处理。
- **If 双方强度差值 ≥ 30（实力悬殊）**: 对手强度标签仍按分类表正常展示，附加强度差提示（如"实力悬殊"），不因差值极端而改变分类逻辑。
- **If 赛后某替补球员未获得出场时间**: 该球员不出现在球员表现摘要列表中，不占用列表空间并标记"未出场"。

## Dependencies

比赛表现 UI 位于 Presentation/MVP 层，是单场比赛各阶段数据的可视化呈现层。它承接比赛竞技系统和联赛与赛事结构系统的数据输出，嵌入主循环 UI 框架定义的 Match Pre / Match Live / Match Result 容器内，为下游新手引导系统提供比赛界面的 UI 锚点。

### Upstream Dependencies

| Dependency | Type | Why it matters | Required interface |
|---|---|---|---|
| `design/gdd/game-concept.md` | Hard | 定义低压力基调、比赛观看体验的核心幻想 | 低压力节奏、"看得懂"的比赛反馈目标 |
| `design/gdd/systems-index.md` | Hard | 定义本系统在 Presentation/MVP 的位置及依赖方向 | 系统层级、优先级、上下游系统列表 |
| `design/gdd/match-competition-system.md` | Hard | 提供赛前阵容/战术数据、赛中关键事件流、赛后结果包和复盘原因标签 | `team_match_strength`、关键事件流（含事件类别和发生时间）、比赛结果包（胜/平/负、比分）、`post_match_growth_tag`、`player_performance_score`、复盘原因标签组、比赛状态机 |
| `design/gdd/league-competition-structure-system.md` | Hard | 提供赛前联赛上下文和赛后积分榜影响数据 | 双方当前排名、比赛轮次、主客场标识、积分榜位置、赛季进度信息、"赛季未结束"标记 |
| `design/gdd/main-loop-ui-framework.md` | Hard | 定义本系统必须嵌入的三个容器和导航规则 | Match Pre / Match Live / Match Result 容器规范、导航规则、`screen_transition_duration_ms`、视觉容器分区、事件优先级队列 |
| `design/gdd/player-development-system.md` | Soft | 赛前阵容中需展示球员属性和状态标签 | 球员当前属性、状态标签、位置适配倾向——本系统只做可视化展示，不定义数据语义 |

| 音频系统 | Soft (provisional) | 赛中关键事件（进球、逆转、终场）需触发音频反馈 | 音频触发时机——该系统未设计，MVP 不集成音频，本系统预留事件触发锚点 |

### Downstream Dependencies

| Dependent system | Type | What it consumes from 比赛表现 UI | What must be back-referenced later |
|---|---|---|---|
| 新手引导系统 | Hard | 赛前/赛中/赛后界面的 UI 锚点、关键操作入口标识、屏幕流转路径 | 必须声明其首场比赛引导的目标界面和提示锚点基于本系统定义的各阶段容器和操作入口 |
| 教程与提示系统 | Soft | 比赛界面的信息层级、各区域标识、操作流程顺序 | 必须声明其提示内容与本系统定义的信息分区和操作顺序一致 |

### Dependency Rules

1. 比赛表现 UI 负责"比赛数据如何呈现、玩家如何观看和理解一场比赛"，不负责"数据是否正确""比赛如何演算""积分如何累积"；这些边界分别服从比赛竞技系统、联赛与赛事结构系统和主循环 UI 框架。
2. 任何下游系统若希望新增比赛界面阶段、改变信息展示优先级、覆盖关键事件视觉权重或修改赛后信息区顺序，必须先回到本系统修订，而不能在本地 GDD 静默覆盖。
3. 主循环 UI 框架定义了本系统的三个嵌入容器——Match Pre、Match Live、Match Result。本系统不得在框架容器外自建独立的比赛查看入口；所有比赛界面必须在框架容器内完成呈现。
4. 当音频系统 GDD 完成后，本节音频系统条目应从 Soft (provisional) 升级为 Hard，并在其 GDD 的 Dependencies 中反向声明对本系统中关键事件触发时机的依赖。
5. 比赛表现 UI 是新手引导系统在"首场比赛体验"中的直接承接者；比赛界面的各阶段入口、关键操作按钮（开赛确认、中场确认、赛后确认）必须具有稳定标识，供引导系统精确指向。
6. 如果比赛竞技系统或联赛与赛事结构系统新增了数据字段或改变了事件类别定义，本系统必须同步更新对应的视觉权重分类和展示规则；反之，如果本系统需要新增展示数据需求，必须回到上游游戏系统确认数据源是否支持。

## Tuning Knobs

本节仅包含比赛表现 UI 拥有的共享调参项。它们控制"比赛界面的事件节奏、视觉权重、信息密度和过渡体验"，不包含比赛演算参数、积分规则、阵容合法性判定或具体的像素尺寸/颜色/字体。

| 调参项 | 控制内容 | 安全范围 | 调高风险 | 调低风险 | 主要影响 |
|---|---|---|---|---|---|
| 最小事件展示间隔 `min_event_display_interval` | 赛中任意两个关键事件呈现之间的最小时间间隔 | 500–1000ms | 间隔过大 → 事件节奏拖沓，比赛观感沉闷 | 间隔过小 → 事件瞬间堆出，失去叙事节奏 | 比赛观看节奏、事件可读性 |
| 基础事件间隔 `base_interval` | 标准比赛节奏下的事件展示基础间隔 | 1500–3000ms | 间隔过大 → 比赛反馈太慢，玩家等待感强 | 间隔过小 → 事件展示过快，玩家来不及阅读 | 事件流节奏、阅读舒适度 |
| 强度因子范围 `intensity_factor_band` | 来自比赛系统的比赛强度对事件间隔的影响幅度 | 0.8–1.2 | 范围过大 → 重要/不重要比赛的节奏差异过于极端 | 范围过小 → 比赛重要性在节奏上无感知 | 重要比赛的特殊感、节奏变化 |
| 比分变化动画时长 `score_change_animation_ms` | 进球后比分变化的视觉强调动画时长 | 800–2000ms | 时长过长 → 动画拖沓，若连续进球会堆积 | 时长过短 → 进球缺乏分量感 | 进球情绪反馈、比赛戏剧性 |
| 中场分隔过渡时长 `halftime_transition_ms` | 上半场结束到中场调整界面的过渡动画时长 | 500–1500ms | 时长过长 → 节奏中断，玩家等待不耐烦 | 时长过短 → 中场切换无感知，上下半场混淆 | 半场节奏感知、阶段切换清晰度 |
| 赛后信息区展示延迟 `post_match_section_reveal_delay` | 赛后各信息区依次展示的渐进延迟间隔 | 200–600ms | 延迟过大 → 赛后信息逐条蹦出太慢，阅读不连贯 | 延迟过小 → 所有信息同时出现，信息过载 | 赛后信息消化节奏、结果揭晓仪式感 |
| 赛前对手强度标签级数 `opponent_strength_label_granularity` | 对手强度对比的分类级数 | 3–5 级 | 级数过多 → 分类过于精细，边界争议增加 | 级数过少 → 对手强弱区分感不足 | 赛前预期管理、对手感知 |
| 对手强度分类阈值 `strength_diff_threshold` | 相邻强度标签之间的 `team_match_strength` 差值阈值 | 8–15 | 阈值过大 → 只有极端差距才显示不同标签 | 阈值过小 → 微小差距就切换标签，不稳定感 | 强度标签分布、信息可信度 |
| 关键事件时间线最大可见条目 `timeline_visible_entries` | 赛中/赛后事件时间线一屏内可见的事件条目数 | 3–8 | 可见过多 → 单屏信息密集，阅读压力大 | 可见过少 → 需频繁滚动，比赛全貌感知弱 | 事件浏览效率、信息密度 |
| 球员表现摘要最大展示人数 `player_performance_max_display` | 赛后球员表现摘要区展示的球员数量上限 | 11–16 | 上限过高 → 列表过长，核心信息被稀释 | 上限过低 → 出场球员被截断，信息不完整 | 赛后信息完整性、浏览效率 |
| 赛后复盘原因标签最大同时展示数 `reason_tags_max_display` | 赛后同时展示的复盘原因标签数量上限 | 2–5 | 上限过高 → 多个原因堆叠，主要原因被稀释 | 上限过低 → 只能看到部分原因，复盘不完整 | 复盘可理解性、原因聚焦度 |
| 比赛离开警告确认方式 `match_exit_warning_mode` | 赛中尝试离开比赛时的警告交互方式 | 简单对话框 / 二次确认对话框 | 无确认 → 可能误触离开比赛 | 二次确认 → 频繁取消时操作繁琐 | 操作安全感、防误触 |
| 赛前默认战术方案数 `default_tactic_options_count` | 赛前战术选择区展示的预设战术方案数量 | 2–5 | 过多 → 选择负担增加，赛前准备时间拉长 | 过少 → 策略选择感不足 | 赛前策略深度、操作效率 |
| 赛后事件时间线默认滚动位置 `post_timeline_default_scroll` | 赛后时间线首次打开时的默认滚动位置 | 顶部（最新）/ 底部（最早）/ 进球锚点 | 默认底部 → 需滚动才能看到最新事件 | 默认顶部 → 缺少"从头回顾"的叙事感 | 赛后阅读体验、叙事流向 |
| 联赛影响提示刷新延迟 `league_impact_refresh_delay` | 赛后联赛系统返回积分榜影响数据后的展示延迟 | 0–500ms | 延迟过大 → 赛后联赛信息出现太慢 | 无延迟 → 与赛后其他信息同时出现时可能被忽略 | 联赛影响感知、信息节奏 |

## Acceptance Criteria

- **GIVEN** 一场比赛节点被触发，玩家进入赛前界面，**WHEN** QA 检查 Match Pre 容器内容，**THEN** 必须展示对手名称、主/客场标识、比赛轮次、双方当前排名、己方首发名单、当前战术方案和开赛确认按钮。
- **GIVEN** 赛前阵容中存在位置未填满或门将缺失等不合法配置，**WHEN** QA 检查开赛按钮状态，**THEN** 开赛按钮必须禁用并显示具体缺失原因（如"缺少门将"）。
- **GIVEN** 赛前阵容满足最低合法条件，**WHEN** QA 点击开赛确认按钮，**THEN** 比赛必须正常开始，界面从 Match Pre 切换至 Match Live。
- **GIVEN** 赛前对手 `team_match_strength` 已知，**WHEN** QA 检查对手信息区，**THEN** 对手强度必须以可读标签展示（"我们是优势方"/"实力相当"/"对手略强于我们"），不展示裸数值。
- **GIVEN** 玩家在赛前切换战术方案，**WHEN** QA 观察战术选择区，**THEN** 战术描述和方案名称必须即时更新，无需额外确认。
- **GIVEN** 比赛正式开始进入上半场，**WHEN** QA 检查 Match Live 界面，**THEN** 必须展示实时比分、比赛阶段指示（上半场）、关键事件时间线和当前比赛时间。
- **GIVEN** 比赛系统产出一个进球事件，**WHEN** QA 观察比分区域和事件时间线，**THEN** 比分变化必须以高于普通事件的视觉权重呈现（比分旁闪烁/比分变化动画），时间线中对应事件卡片显著突出。
- **GIVEN** 比赛系统连续产出多个关键事件，**WHEN** QA 观察事件时间线，**THEN** 每个事件必须按时间顺序展示，事件之间有时间流逝的视觉间隔（≥500ms），不瞬间堆出。
- **GIVEN** 上半场结束，**WHEN** QA 检查界面状态，**THEN** 必须出现明确的中场分隔线或阶段切换提示，Halftime Adjustment 入口可用。
- **GIVEN** 玩家在中场调整界面修改阵容并确认，**WHEN** QA 检查确认反馈，**THEN** 必须明确提示"调整已生效，下半场即将开始"，下半场使用更新后的阵容。
- **GIVEN** 玩家在中场调整界面修改后未确认就返回，**WHEN** QA 观察系统响应，**THEN** 必须弹出确认对话框"放弃本次调整？"；直接返回保留原阵容。
- **GIVEN** 下半场完成且终场结果确定，**WHEN** QA 检查 Match Result 界面，**THEN** 终场比分必须在最显眼位置展示，且按固定顺序依次展示：比分 → 胜负原因标签 → 关键事件时间线 → 球员表现摘要 → 联赛影响提示 → 确认按钮。
- **GIVEN** 赛后界面展示，**WHEN** QA 检查复盘原因标签，**THEN** 多个原因同时命中时全部展示且按优先级排序，不只展示第一个。
- **GIVEN** 赛后界面展示，**WHEN** QA 滚动关键事件时间线，**THEN** 必须可查看本场比赛全部关键事件，最新事件默认可见。
- **GIVEN** 赛后界面展示，**WHEN** QA 检查球员表现摘要，**THEN** 每名出场球员必须展示评分和关键数据（进球/助攻如有），未出场替补不出现在列表中。
- **GIVEN** 联赛系统返回"赛季未结束"标记，**WHEN** QA 检查赛后联赛影响提示区，**THEN** 必须展示当前积分榜位置并附带"赛季未结束，排名可能变化"标记，不展示可能误导的锁定信息。
- **GIVEN** 比赛处于 Match Live 状态，**WHEN** QA 尝试通过任意方式离开比赛界面，**THEN** 系统必须阻止离开或给出明确警告，不得允许静默退出。
- **GIVEN** 玩家在赛后界面点击确认按钮，**WHEN** QA 检查导航结果，**THEN** 必须返回主界面（Home），且主界面数据反映赛后最新状态。
- **GIVEN** 赛前/赛中/赛后各阶段切换，**WHEN** QA 观察过渡效果，**THEN** 过渡动画在 `screen_transition_duration_ms` 时长内完成，不出现白屏、黑屏或全屏加载转场。
- **GIVEN** 玩家从赛前准备到赛后确认完成一场完整比赛，**WHEN** QA 检查整体体验，**THEN** 玩家必须能在赛后回答"发生了什么、为什么会这样、我赛前哪些选择影响了结果"。
